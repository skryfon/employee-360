## Findings

### 🔴 Critical
- [x] `backend/internal/infrastructure/service/mail_service.go:230-232` (`buildMIMEMessage`) — the `From`, `To`, and `Subject` MIME headers are built via raw `fmt.Sprintf("...: %s\r\n", value)` with no stripping or rejection of embedded `\r`/`\n` in `from`, `to`, or `subject`. Go's `net/smtp` only validates SMTP *command* lines (`MAIL FROM`/`RCPT TO`/`HELO`) against embedded CRLF — it does not touch the raw `DATA` payload built here. Since `subject` can come straight from caller-supplied `msg.Subject` (optionally template-rendered from `msg.TemplateData` at `mail_service.go:104-114`, e.g. a tenant/role name) and `msg.To` is an arbitrary recipient string, a value containing `\r\n` (e.g. a tenant name entered by an admin, or a maliciously-crafted invite email address once B4/C1 usecases start feeding this function) can inject arbitrary additional headers (`Bcc:`, a second `To:`, etc.) or corrupt the MIME structure — classic email header injection (CWE-93). Fix: reject or strip `\r`/`\n` (and ideally other control characters) from `from`, `to`, and `subject` before they're written into the header block — e.g. a small `sanitizeHeaderValue`/`validateNoCRLF` helper called at the top of `buildMIMEMessage`, returning an error rather than silently building a malformed/hostile message. **(resolved in `75cb98a`** — added `validateNoCRLF` helper called at the top of `buildMIMEMessage` for `from`/`to`/`subject`, returning an error rather than stripping; new tests `TestSMTPMailService_Send_RejectsCRLFInjection_To`, `TestSMTPMailService_Send_RejectsCRLFInjection_Subject`, and `TestSMTPMailService_Send_RejectsCRLFInjection_TemplateRenderedSubject` (the last covering CRLF smuggled in via `TemplateData` through a custom subject template) all assert `Send()` errors and that nothing reaches the mock SMTP server.)

### 🟡 Major
- [x] `backend/internal/infrastructure/service/mail_service.go:323-330` (`sendViaSMTP`) — when `cfg.UseTLS` is explicitly `true` on a non-implicit-TLS port (587/25/2525) but the server doesn't advertise/support `STARTTLS`, the code silently proceeds without upgrading the connection instead of failing closed. Go's `net/smtp.PlainAuth` does refuse to send credentials over a non-TLS, non-localhost connection (so the credential-leak case is covered), but the message body itself — including password-reset URLs/tokens — would still be transmitted in cleartext with no error surfaced, defeating the operator's explicit `SMTP_USE_TLS=true` intent. This matters specifically because this ticket's whole premise is "swap providers via config" (SES/Postmark/self-hosted relay over STARTTLS on 587 are realistic targets), so a stripped/unsupported STARTTLS on a provider swap would degrade silently. Fix: if `cfg.UseTLS` is true and STARTTLS isn't available or fails, return an error instead of continuing in plaintext. **(resolved in `75cb98a`** — `sendViaSMTP`'s STARTTLS branch now fails closed: if `cfg.UseTLS` is true and the server doesn't advertise `STARTTLS` on a non-implicit-TLS port, `Send()` returns an error instead of continuing in plaintext (the `client.StartTLS` failure path already errored). Covered by `TestSMTPMailService_SendViaSMTP_STARTTLSRequested_FailsClosedWhenUnsupported`.)
- [x] `backend/internal/infrastructure/service/mail_service_test.go` — all 6 tests run against a plaintext mock SMTP server (`UseTLS: false`, no TLS handshake). The two TLS code paths in `sendViaSMTP` — implicit TLS (port 465, the actual production default per `.env.example`/`config.yaml.example`) and STARTTLS (port 587) — have zero test coverage. A regression in either path (e.g. the `isImplicitTLS` heuristic below) would only surface against a real provider in production. **(resolved in `75cb98a`** — added `TestSMTPMailService_SendViaSMTP_ImplicitTLSPort_UsesTLSDialer` (port 465, asserts the injected `tlsDialer` hook is used and the plain `dialer` is not, full protocol completes) and `TestSMTPMailService_SendViaSMTP_STARTTLSRequested_FailsClosedWhenUnsupported` (port 587, asserts the plain `dialer` is used for the initial connection and the TLS-upgrade fail-closed path is hit). Per the review's own guidance, these use the `WithCustomDialer` injection point to assert correct dialer selection per `cfg.Port`/`cfg.UseTLS` rather than performing a real TLS handshake against a self-signed cert.)
- [x] `backend/internal/infrastructure/service/mail_service.go:106-114` — when the optional custom-subject template fails to parse or execute, both errors are silently swallowed (`if err == nil { subject = ... }`) and the original un-rendered subject string (potentially containing literal `{{...}}` template syntax) is sent to the recipient with no error returned or logged. Prefer propagating the error like `renderSubjectTemplate`/`renderTextTemplate`/`renderHTMLTemplate` already do, rather than silently degrading the subject line. **(resolved in `75cb98a`** — both the `Parse` and `Execute` errors are now propagated from `Send()` via `fmt.Errorf(...: %w, err)`, matching the other render methods. Covered by `TestSMTPMailService_Send_CustomSubjectTemplate_ParseError`.)

### 🟢 Minor
- [x] `backend/internal/infrastructure/service/mail_service.go:288` — `isImplicitTLS` is derived from a hardcoded port allowlist (`!= 587 && != 25 && != 1025 && != 2525`) mixed with `cfg.UseTLS`, rather than a single explicit config flag (e.g. `smtp.tls_mode: implicit|starttls|none`). Works for the three providers named in this ticket (Resend/Mailpit, tested indirectly via defaults) but is brittle for an unlisted self-hosted relay on a nonstandard port — the exact "provider swap via config only" scenario this ticket is meant to support cleanly. **(resolved in `75cb98a`** — no new config surface added (avoiding scope creep as noted); the port allowlist was extracted into two named, commented package-level vars (`starttlsPorts`, `plaintextDevPorts`) explaining the reasoning for each port, and both `isImplicitTLS` and the STARTTLS-attempt condition now reference them instead of inline magic numbers.)
- [x] `backend/internal/infrastructure/service/mail_service.go:388-400` — `normalizeTemplateData`'s snake_case↔CamelCase alias table is a hand-maintained, growing lookup map baked into the infra layer; every new template variable added by a future template needs a matching entry here or it silently won't get the other casing's alias. Consider documenting this requirement inline, or replacing the `map[string]interface{}` dual-casing convention with a typed per-template data struct later. **(resolved in `75cb98a`** — added a doc comment above the `mappings` map explaining that a new template variable needs a corresponding snake_case/CamelCase entry to get both casing aliases.)
